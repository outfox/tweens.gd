# C# benchmark follow-up and optimization results

The `benchmarks` branch adds concrete struct start overloads, removes allocation
from `Group.IsPaused`, reduces execution-plan construction allocations, and skips
redundant scheduler list writes. The original measurements are preserved in the
[initial report](2026-10-08-optimization.md).

## What changed

Structs still box when passed as an interface. The original start API accepted
`ITweenDefinition<TTarget, TValue>`, so starting a concrete immutable definition
allocated an interface box. Generated `in Tweens.X` overloads now retain the
definition's concrete type through a constrained generic call to
`CreatePlayback`. Both scheduler starts and node/resource extension starts have
these overloads. Existing interface APIs remain useful for heterogeneous
collections; placing structs in those collections still boxes them. Playback
snapshots and handles continue to allocate by design.

`Group.IsPaused` now scans members directly, ignores terminal members, exits on
the first active unpaused member, and returns false when none remain active.
It no longer creates a filtered array on every read. Groups have dedicated
polling and creation benchmarks. Neither the original flat update workloads
nor the new per-definition catalog updates run groups.

Execution-plan construction now collects finite boundaries into one buffer,
sorts it, and removes duplicates in place. An indexed scan replaces the
activation path's `Skip(...).Any(...)`. Scheduler compaction avoids writing
survivors back into slots they already occupy. These changes preserve the
timeline state machine and lifetime checks.

## Measured creation and polling improvements

The original 34 cases were repeated with two launches, five warmups and ten
measurement iterations per launch, targeting 100 ms. Creation still uses one
128-start invocation per iteration and reports **per tween**. Other lifecycle
rows include scheduler construction and disposal. Full samples, uncertainty and
diagnostics are in the [repeat evidence](2026-10-08-followup-measurements.json).

| Operation | Before ns | After ns | Before B | After B |
| --- | ---: | ---: | ---: | ---: |
| Concrete struct start | 2,999.66 | 2,222.70 | 2,063 | 1,063 |
| Preboxed definition start | 2,907.60 | 2,178.54 | 1,687 | 1,063 |
| Mutable definition start | 2,679.24 | 1,941.82 | 1,687 | 1,063 |
| Managed start/cancel | 263.00 | 175.08 | 1,472 | 1,040 |
| Managed start/complete | 487.36 | 377.86 | 1,720 | 1,048 |
| Four-entry chain start/cancel | 1,969.52 | 1,291.36 | 8,272 | 4,920 |
| Four-entry group start/cancel | 1,317.99 | 831.58 | 6,744 | 4,248 |
| `IsPaused`, four members | 30.61 | 3.58 | 104 | 0 |
| `IsPaused`, 100 members | 574.41 | 69.61 | 872 | 0 |

Concrete starts are about 26% faster and allocate 48% less in this workload.
The previous 376-byte gap between concrete and preboxed starts is gone; the
remaining 624-byte saving common to both comes from plan construction. Group
polling is about eight times faster and allocation-free. Requesting an `End`
task still adds 96 bytes to managed start/cancel; direct custom-skew easing
still allocates 360 bytes per evaluation.

These changes do **not** establish recovery of the historical slowdown. Engine
results are mixed: 1,000-position updates changed from 397.48 to 394.83 µs,
while 10,000-color updates changed from 4.47 to 4.92 ms. Creation savings must
not be presented as an equivalent frame-time gain.

## Managed update comparison with isolated fixtures

The initial managed fixture kept three schedulers resident while timing one.
The 34-case repeat showed unexpectedly slower large managed workloads, despite
lower construction allocations. Controlled source variants ruled out the new
compaction loop and activation-helper inlining as explanations. Changing plan
construction affected the results, suggesting sensitivity to setup/heap layout;
the precise cache/GC mechanism was not profiled.

The fixture now creates only the selected workload, using method-specific
setup. This removes unused schedulers and makes `Count` the actual resident
tween count. A matched comparison used this corrected fixture on both sides:
original plan and compaction from `eccfabd`, versus the optimized versions from
`2a21ee6`, holding other changes constant. Two launches, ten warmups and fifteen
measurement iterations per launch, targeting 100 ms, produced:

| Workload | Count | Original µs | Optimized µs | Less time |
| --- | ---: | ---: | ---: | ---: |
| Absolute | 100 | 7.251 | 6.849 | 5.5% |
| Relative | 100 | 8.145 | 7.689 | 5.6% |
| Callback | 100 | 7.278 | 6.806 | 6.5% |
| Absolute | 1,000 | 74.979 | 70.905 | 5.4% |
| Relative | 1,000 | 83.684 | 78.404 | 6.3% |
| Callback | 1,000 | 74.967 | 70.625 | 5.8% |
| Absolute | 10,000 | 756.407 | 706.668 | 6.6% |
| Relative | 10,000 | 843.686 | 826.690 | 2.0% |
| Callback | 10,000 | 755.459 | 704.404 | 6.8% |

The smaller relative-case difference needs caution given its variance. Full
samples, confidence intervals, diagnostics and all temporary diagnostic
variants are preserved in [managed isolation evidence](2026-10-08-managed-isolation.json).
The earlier three-scheduler results remain available for audit, but should not
be compared directly with the corrected fixture as an optimization percentage.
The library was restored byte-for-byte to the `2a21ee6` implementation after
these experiments. Independent warmed allocation checks use the corrected
fixtures as well.

## Catalog methodology

The full catalog was measured at library revision `2a21ee6`. All 1,444 cases
completed successfully. The [full ranking](2026-10-08-catalog-ranking.md),
[CSV](2026-10-08-catalog-ranking.csv), and
[portable JSON](2026-10-08-catalog-ranking.json) preserve every baseline pair.
All managed thread-pool work and monitor-contention counters were zero.

The catalog discovers all 331 nongeneric definitions, all seven supported value
types for each of three shader families, and nine custom-property value types:
361 concrete cases. Each runs at 100 and 1,000 targets with both `TweenUpdate`
and `DirectWrite`, giving 1,444 BenchmarkDotNet cases and 722 paired rankings.
New nongeneric definitions are discovered automatically; an unknown generic
family fails setup until fixtures are provided.

The baseline uses the same property setter and interpolation operation on the
same target type. Component setters retain their read/modify/write behavior.
Resources use actual resources; custom properties use plain managed objects;
callback definitions use callback writes. Setup validates representative direct
and tween values and cleanup rejects terminal/faulted handles or engine errors.
Reflection, construction, engine startup and shutdown are outside timing.

Every benchmark class has `MemoryDiagnoser` and `ThreadingDiagnoser`. Allocation
counts cover managed allocations. Threading counters cover managed thread-pool
work and monitor contention, not native Godot worker threads. The catalog runs
headless: rendering, GPU work and native retained memory are outside its scope.

The full catalog is a short-run screen: one process launch, three warmup and
three measurement iterations, with a 100 ms target iteration time. Rankings
retain sample values and confidence intervals; small differences and high
variance need longer confirmation. The outlier flag uses cost per target above
Q3 + 3×IQR within each target count. Ratios are ratios of means, and overhead is
the difference between tween and direct-write means, divided by target count.

## Outliers and confirmation

Representative short-run results at 1,000 targets, in microseconds per frame:

| Definition | Tween | Direct write | Interpretation |
| --- | ---: | ---: | --- |
| Canvas instance shader, Color | 1,845.89 | 138.69 | Very wide uncertainty; longer run below |
| Canvas instance shader, float | 1,810.68 | 64.07 | Very wide uncertainty; longer run below |
| Geometry instance shader, float | 991.36 | 64.47 | Allocation anomaly in this short run |
| PathFollow3DProgressRatio | 863.84 | 483.43 | Expensive direct target operation as well |
| ControlOffsets | 720.67 | 326.04 | Four component writes carry substantial native cost |
| Position2D | 398.83 | 31.65 | Representative ordinary node property |
| MaterialRoughness | 119.31 | 29.81 | Resource path has lower overall cost |

The three allocation anomalies were Canvas Vector4 at 100 targets (3,201 B),
Geometry double at 100 (2,401 B), and Geometry float at 1,000 (24,008 B).
These are compatible with one value box per tween plus harness overhead, but
they were **not reproduced** in the longer confirmation runs. Generic shader
conversion/interpolation contains boxing-shaped source constructs; establishing
which survive a particular JIT tier requires allocation stacks or disassembly.

The [14-case confirmation](2026-10-08-catalog-confirmation.json) used two
launches, ten warmups and fifteen measurement iterations. Its actual iteration
target was 100 ms: the catalog attribute overrode the CLI's requested 250 ms.
The host now expresses that budget as a default job, allowing CLI overrides.
At 1,000 targets, Canvas Color/float/Vector4 settled at 598.08/593.66/607.68 µs;
Geometry double/float at 789.73/794.91 µs. Reported allocations were 5 B per
**frame**, not per tween. At 100 targets, those shader cases reported 0–1 B.
Treat the short-run shader allocation spikes and the top two CPU rankings as
warmup/process-sensitive observations, not steady-state guarantees.

PathFollow3DProgressRatio remained expensive in confirmation: 872.44 ± 11.27 µs
for tweens versus 469.62 ± 2.20 µs for direct writes at 1,000 targets, a 1.86×
ratio of means. Its direct target operation accounts for about half the cost.
Shader confirmation selected updates only, so no newly paired shader ratios
are claimed. All confirmation threading counters were zero.

## Harness and validation

The full catalog completed all 1,444 cases in 36m39s of benchmark-run time;
total wall time was 47m13s, including build and report generation. A managed
stack inspection found repeated logical-group scans during BDN baseline-table
construction. The host now caches the unchanged BDN grouping function by case
universe and case. `--verify-orderer` checks all 722 baseline pairs and equality
with BDN's grouping both with and without baseline cases. This changes report
generation, not measured code. See BDN's
[grouping implementation](https://github.com/dotnet/BenchmarkDotNet/blob/v0.15.8/src/BenchmarkDotNet/Order/DefaultOrderer.cs).

- 1,814 headless tests passed on each of the net10.0 and net8.0 library builds.
- Headless/lifecycle coverage passed: 99.48% lines, 95.20% branches.
- All 361 catalog fixtures passed value, lifetime and engine-error checks.
- Independent warmed checks reported zero allocated bytes over 1,024 frames of
  1,000 absolute, relative, callback and Node2D position tweens.
- The final four-case smoke run verified that `--iterationTime 250` overrides
  the catalog's 100 ms default.
- Generated C# definitions, GDScript catalog and addon UIDs passed checks.
- All 63 C# documentation examples compiled with the new overloads.
- Ranking-export tests passed, including complete names, missing measurements,
  missing baselines and missing diagnostic rejection.

Full raw logs and BDN exports remain in `artifacts/bdn-*` locally. The portable
JSON reports retain samples and environment information; the catalog CSV
supports sorting and filtering all definitions without relying on truncated
BDN parameter display names.

## Remaining optimization potential

- Specialize the execution plan for a single independent tween. Its general
  entry/boundary machinery is unnecessary for the common one-leaf case, but a
  fast path must preserve negative delays, reverse playback, callback
  reentrancy, cancellation and fill behavior.
- Avoid constructing standalone plans for leaves that will immediately become
  part of a chain. Chain creation currently pays for those temporary plans as
  well as the chain's final plan.
- Investigate repeated native lifetime and pause queries with a CPU profile.
  Cache only across intervals where user callbacks cannot invalidate the
  assumptions; removing the checks wholesale would break lifecycle guarantees.
- Direct custom-skew `Easing.Evaluate` builds a composition on each call. Tween
  playback already captures its evaluator. A reusable public sampler would
  address repeated standalone evaluation without an unbounded global cache.

Allocation totals and controlled comparisons identify candidate sites; they
are not allocation-stack traces or percentages from a sampled CPU profile.
